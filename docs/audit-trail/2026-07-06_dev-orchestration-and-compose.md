# 2026-07-06 — Init generates dev orchestration + docker-compose

**Date/time:** 2026-07-06

Initialized repos now come with (a) a root `pnpm run dev` that runs every
selected stack together with hot reload, and (b) a `docker-compose.yml` +
per-stack `Dockerfile.dev` so the whole stack (frontend + backend + db) is
buildable and runnable under Docker, with migrations applied automatically. Both
paths are generated by `scripts/prune.mjs` at init, so they're always correct for
the selected stack combination and repo shape (hoisted vs workspace).

## Decisions (confirmed with the user)

- **Compose is composed per selection** — each block is emitted only when its
  piece is present: a `web`/`api`/`api-py` service per selected stack, and a
  `postgres` service (+ one-shot `migrate` service + named volume) ONLY when
  `--db` was passed. A frontend-only repo gets just `web`; a backend+db repo gets
  `api` + `postgres` + `migrate`.
- **`concurrently`** drives the native multi-stack `pnpm run dev` (labelled,
  colour-coded streams). Single-stack repos just run that stack's dev directly
  (no dep added).
- **Ports fixed to avoid the next/fastify 3000 collision:** frontend 3000, TS
  backend 4000, Python backend 8000, Postgres host 5452 → container 5432.
- **DB env contract:** modelled the compose on the user's example (postgres
  service + healthcheck + app + named volume) but wired it with the skeleton's
  OWN contract — a single `DATABASE_URL` (`postgres://` for TS,
  `postgresql+asyncpg://` for Python) — not the example's `DB_HOST`/`DB_USER`
  split. That's the "ignore repo-specific stuff" instruction applied to env shape.

## Files created (factory-only templates, deleted with scripts/ at init)

- `scripts/templates/dev/Dockerfile.dev.ts-backend`
- `scripts/templates/dev/Dockerfile.dev.next-frontend`
- `scripts/templates/dev/Dockerfile.dev.py-backend`

Each is a single-stage dev image (deps-from-manifest, then bind-mounted source
for hot reload). Base image digests match the production Dockerfiles so
Dependabot bumps both together. No `--frozen-lockfile` (a workspace member has
no local pnpm lock — single root lock); Python uses `poetry.lock*` glob (the
`--db` path regenerates the lock post-init).

## Files updated

- `scripts/prune.mjs`:

    `composeYaml` (per-selection compose incl. postgres + one-shot migrate),
    `migrateCommand` (drizzle-kit / alembic), `copyDevDockerfiles`.
  - `hoistedPackageJson` + `workspacePackageJson` now take `db`, add a root `dev`

    when `--db` is on.

    Dockerfiles and write `docker-compose.yml`.
  - `cloneReadme` + `workspaceReadme` document native dev, docker, ports, and the
    migration flow per shape; the workspace README's Docker note now distinguishes
    the dev flow from the production single-service Dockerfile caveat.

## How it works

- **Native:** `pnpm run dev` → `concurrently -k -n web,api ... "pnpm --filter web
  run dev" "PORT=4000 pnpm --filter api run dev"` (or a single command for a
  one-stack repo; Python via `poetry ... uvicorn --reload`).
- **Docker:** `docker compose up --build`. With `--db`, startup order is
  postgres (healthy) → `migrate` (runs `drizzle-kit migrate` / `alembic upgrade
  head`, exits) → the db-owning app (`depends_on:
  migrate: service_completed_successfully`). Source is bind-mounted; an anonymous
  volume protects the image's installed deps.

## Side effects considered

- **Both repo shapes handled.** Build context = the service dir in either shape
  (hoisted root, or the member dir), each of which has its own `package.json`.
  Sidesteps the workspace single-root-lockfile problem the production Dockerfiles
  punt on (documented distinctly in the workspace README).
- **No pnpm workspace membership for Python.** The py backend's dev/migrate run
  via `poetry -C services/api-py` (or `poetry run` when hoisted), never `pnpm
  --filter`.
- **Lint/format gate unaffected.** Biome's generated config has
  `ignoreUnknown: true` and handles only js/ts/json/css — `docker-compose.yml`
  (YAML) and `Dockerfile.dev` (no extension) are ignored, so the post-init
  `pnpm run lint`/`format:check` gate stays green.
- **AI-config drift untouched** — only `scripts/` + templates changed, nothing
  under `ai/`. `ai-build --check` still reports 27 files in sync.
- **CI scaffold matrix** (`.github/workflows/ci.yml`) bootstraps every combo and
  runs its full gate; my additions ride that. The matrix's `docker build .` step
  uses the PRODUCTION Dockerfile (unchanged); the new `Dockerfile.dev` /
  `docker-compose.yml` are inert to it.

## Issues spotted during implementation

- First compose draft set `build.context` to the repo ROOT in workspace shape to
  reach the root lockfile, but that made per-member `COPY` ambiguous. Switched to
  per-service-dir context + `pnpm install` without `--frozen-lockfile` — simpler
  and shape-agnostic (members have their own `package.json`, no local lock).
- The user's example implied "migrations run on start"; a bare dev app container
  doesn't do that. Added an explicit one-shot `migrate` service the app depends
  on, so `docker compose up` genuinely applies migrations before serving —
  matching the "buildable via docker with migrations" requirement.
